# AST-10 — 闭环服务与调试期全量留档

## 目标

把 Project Astero 从一次性脚本组合成可持续运行、可恢复、可诊断的闭环服务。采集、唤醒、端点检测、ASR、对话编排、知识与记忆、任务状态、留档和播放协调等产品逻辑都由本仓库实现并拥有；模型、设备及既有本地 TTS/播放进程通过明确的适配器接入。

本阶段处于本机调试期：每次服务接收到的音频均完整留档，便于回放和定位链路问题。暂不设 TTL，也不自动清除留档；保留期限及清理策略后续另行决定。

## 验收路径

本机自动验收使用声学回环，不以手工注入 PCM 或纯 mock 代替：

```text
验收驱动器 → 本地 TTS 播放“Astero”及测试指令
            → Echo 麦克风采集 → Astero 服务处理
            → ASR → 对话/agent → 本地 TTS 播报回答
            → 验收驱动器核对各阶段结果和任务终态
```

Echo 放在电脑扬声器附近，使本地 TTS 的发音由真实麦克风采集。验收驱动器可以发起轮次、选择已知测试文本并收集结构化结果；验收结果必须注明该路径使用合成语音，不能据此替代真人唤醒率或真实用户可懂度评估。

## 范围

### 1. 仓库内的服务边界

- 提供可独立启动和停止的 Astero Service；语音入口、CLI、验收驱动器及未来其他 agent 使用同一个应用层接口。
- 将当前 `live.py` 中的设备操作、模型初始化和轮次协调拆分到有清晰职责的模块；现有 `astero/orchestrator.py` 保持面向依赖注入的轮次编排，不直接承担设备生命周期、持久化或知识检索。
- 提供明确的请求/响应类型和状态查询：轮次 ID、session ID、阶段状态、最终状态、错误类别和阶段耗时。`accepted`/`queued` 不代表完成。
- 全流程使用统一 trace ID/turn ID，记录从音频入站、处理、上下文检索、LLM 请求与返回、TTS 排队与播放终态到服务返回的开始时间、结束时间、耗时、重试和失败。耗时使用单调时钟计算；结构化 logging 不能泄露凭据或将私人正文写到普通日志。
- 服务生命周期包括启动依赖检查、设备断开/重连处理、优雅退出和重启恢复。外部模型与本地 TTS 可以是基础设施，但面向产品的策略、编排和状态逻辑由本仓库掌握。
- 运行入口和服务协议先采用本机使用边界。若采用 HTTP，默认只绑定 loopback；不得把无鉴权的服务暴露到局域网。

### 2. 调试期全量音频留档

- 对每次服务收到的麦克风音频进行完整、无静默裁剪的留档，包含当前调试监听会话收到的帧；保留时间戳、序号、采样率、通道数、采样格式和设备/采集会话元数据，以便重建输入时间线。
- 保存原始采集数据，并保存实际送入唤醒、VAD 和 ASR 的派生音频或足够重建这些输入的转换结果；索引要能把音频片段与轮次、唤醒、端点及 ASR 结果关联起来。
- 同轮完整保存调试所需的阶段内容：唤醒分数/时间、VAD 与端点边界、ASR 文本、实际提交给 agent 的请求及其回复、TTS 请求/任务 ID/终态、失败原因和耗时。凭据、认证头及密钥必须剔除；其余调试数据留在本机受限目录。
- 留档数据写入可配置的本机持久数据目录，默认位于仓库之外；文件权限限于当前用户。代码、schema、读取/查询/导出逻辑和留档索引全部在本仓库实现，数据文件不提交 Git。
- 留档写入失败必须可见并体现在诊断状态中；不得静默丢弃音频后仍报告本轮留档完整。存储空间不足时显式告警/失败，不自动删除旧数据。
- 本阶段不实现 TTL、自动清理、云同步或默认上传。后续 TTL 决策不得改变本阶段“当前调试数据全量保存”的验收要求。

### 3. 持久会话、知识与记忆

- 首版采用轻量本地持久存储（建议 SQLite，含 schema migration），服务重启后恢复 session、轮次索引和用户明确选择保留的状态。
- 区分三类数据：原始音频/本轮调试记录、短期会话上下文、可跨会话的长期记忆；再将经整理的知识条目与用户记忆分开管理。
- 知识条目和记忆均记录来源、创建/更新时间及可检索标识；agent 使用检索接口获取相关内容，回答依据可追溯。第一版可用 SQLite FTS，不要求先引入 embedding 或向量数据库。
- 提供查看、按 session 查询、导出和显式删除的存储接口。音频在 AST-10 中依照调试要求全量留存；TTL 与自动清理留待后续 milestone。
- 将 LLM/Codex 对话调用封装为可替换 provider adapter；provider 不拥有 session、记忆、知识或任务生命周期。

### 4. 运维与安全边界

- 结构化诊断包含轮次 ID、阶段、耗时、错误类型、重试信息和留档完整性；避免把凭据写入日志。
- 为本机服务定义配置、健康/就绪状态、状态目录、优雅关闭和重启行为。
- 保持工具执行默认关闭；服务化不等于开放任意 shell 或未经确认的外部操作。
- 每轮同时保存可查询的阶段 trace 与总耗时摘要。音频帧级时间线放在调试归档，通用日志按有界批次记录连续采集数据，避免每帧刷屏。

## 不纳入 AST-10

- TTL、自动清理、云端备份/同步和跨机器远程访问。
- 向量数据库、复杂自动记忆提取、多个 agent 自主协作和任意工具执行。
- AEC、全双工打断、音乐混音，以及真人远场唤醒指标的完整验收。
- 将合成 TTS 声学回环结果宣称为真人语音验收。

## 验收标准

1. 一条本机 TTS 合成唤醒词和指令经 Echo 麦克风进入 Astero 服务，完成唤醒、语音端点、ASR、真实已授权对话后端、TTS 播报；留存各阶段结果并能核对最终任务状态。
2. 验收可从服务 API/应用接口触发并取得关联的轮次 ID；不能只调用内部函数、直接注入识别文本或使用 mock 作为闭环通过证据。
3. 麦克风调试监听会话收到的原始音频完整可回放，帧元数据和处理阶段可关联；留档目录在服务重启后仍可查询，且位于仓库外。
4. 服务重启后 session 和持久索引可恢复；不同 session 的上下文、记忆和检索互相隔离。删除接口对选定记录有效。
5. 检查采集断开、模型/LLM/TTS 失败、服务重启、磁盘写入失败和空间不足时的状态与诊断；不得虚报完成或留档成功。
6. 启动时依赖检查和服务健康状态可区分“可接收请求”与“语音链路全部就绪”；播放 `completed` 仅表示播放器完成，声学听感单独记录。
7. 一次请求从服务入站到最终返回的 trace ID 不变；每个阶段的开始/结束、耗时、重试与错误均可查询，LLM 和 TTS 阶段另有耗时及终态；总耗时由单调时钟计算。
8. 记录本机声学回环的输入文本、合成语音来源、识别结果、关键阶段耗时、Bridge/TTS 终态和留档文件索引；不把模型权重、密钥或个人设备标识提交仓库。

## 设计决策待落地

- 服务采用长期运行进程加本机 HTTP API，还是先用本机 Unix socket/嵌入式应用接口；不论传输如何，领域接口和状态定义必须独立于传输。
- 选择统一音频归档容器和索引格式，并明确原始多通道 PCM 与派生单声道音频的版本标识。
- “全量留档”按一次调试监听会话定义：从采集打开到关闭保存全部输入帧，包括静音、唤醒前音频和未形成完整 utterance 的尾段，避免 VAD/唤醒逻辑截断诊断数据。
- 明确知识导入格式、来源追踪和首版记忆写入规则；不自动把所有转录提升为长期记忆。
