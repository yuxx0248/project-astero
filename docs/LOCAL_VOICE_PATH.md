# 本机语音通路：现状与实施顺序

记录日期：2026-11-18。本阶段使用当前 Fedora ARM64 电脑和 USB 连接的 Echo Dot 2，不依赖 Xeon。目标是用户说出 **Astero** 唤醒后，对 Dot 说话，由本机识别、发送给 LLM，再通过 Voice Bridge 从电脑默认扬声器播放回复。手动触发和固定回复只用于隔离测试，不能代替包含唤醒与 LLM 的完整验收。

## 拟定数据流

```text
Dot 麦克风阵列（原始 PCM）
  → USB / ADB 采集与传输
  → 本机选通道 / 格式转换
  → 本机开源关键词检测：Astero → 前置缓冲 / VAD / 端点检测
  → 本机中文或英文 ASR → 转录文本 → LLM → 回复文本
  → Voice Bridge POST /announce → 本机 Qwen3-TTS → paplay
  → 电脑默认扬声器 → 用户听到回复
```

这是一项本机测试选择：**唤醒检测和语音转文字先在电脑上运行**，Dot 负责采集；并非已经验证 Dot 自身能做识别。LLM 可以运行在本机或通过用户授权的服务调用；具体后端尚未确定。Voice Bridge 当前负责文字到语音及播放，不接收麦克风音频，也不提供语音识别或对话生成。后续再评估网络传输、Xeon 和其他输出设备。

| 环节 | 仓库原有候选 | 当前状态 |
| --- | --- | --- |
| 唤醒词 | openWakeWord 自定义模型，或 sherpa-onnx KWS | 没有提供或验证 `Astero` 模型；需验证自定义关键词、语言和 ARM64 运行能力 |
| VAD / 端点检测 | Silero VAD，或 sherpa-onnx | 未部署或验证；需与采样格式、暂停容忍和前置缓冲配合 |
| 中英文 ASR | sherpa-onnx 的中英文模型，或经过测试的替代方案 | 未指定具体模型或版本，也未验证在本机的识别质量及速度 |

## 已确认

- Echo Dot 2（RS03QR / biscuit）已解锁，USB ADB 可 root 访问。PCM 设备可读取 16 kHz、9 通道、S24_3LE 数据，0–6 通道有非零信号；参见 [操作记录](ECHO_DOT_2_INSTRUCTIONS.md)。这还不证明录到了可辨认的人声。
- 原厂 `mixer` 通常占用 PCM 设备；实验时停止后必须恢复。自带 `tinycap` 直接使用目标格式失败，临时 `LD_PRELOAD` 方式采到了数据，但它不是经过长期验证的采集程序。
- Voice Bridge 源码位于本机 `/home/zuohang/workspace/voice-bridge`，已检查的提交为 `afca31f`。2026-11-18 检查时 `127.0.0.1:8765/health` 返回 `status: ok`、`tts_ready: true`，本机 Qwen3-TTS 服务的健康检查也返回 `ok`。健康检查不证明用户实际听见声音。
- Voice Bridge 的 `POST /announce` 接收 JSON `text`，可选 `voice` 和 `style`；HTTP 202 仅表示入队。使用 `GET /announcements/{id}` 等待 `completed` 或 `failed`。服务串行合成并通过 `paplay` 向当时的默认音频设备播放；当前已观察到电脑内置扬声器为默认 sink。播放器完成也需要用户听感确认。
- 本次提交了一条简短中文测试播报，任务从 `queued` 到 `completed`，说明 TTS 和播放器流程报告成功；用户是否听到尚未确认，也不是从 Dot 输入开始的完整语音测试。
- Bridge 和 TTS 仅绑定本机回环地址；Bridge 本身不做鉴权，不应直接暴露到局域网。参考其本机 README 和 `/home/zuohang/agents/SERVICES.md`，使用前重新检查服务状态。

## 仍缺的部分

1. **可重复的人声采集**：独立、可恢复的 Dot 采集器，以及稳定地把 PCM 通过 USB 带到本机。需处理异常退出时恢复 `mixer`、USB 断连、音频权限及噪声；不能依赖实验性临时注入。用用户已知的说话内容确认语音清晰，而非只看非零采样。
2. **输入处理**：正确解码 24 位打包的 9 通道 PCM、选择一个已验证的麦克风通道或可解释的混合方式，转换到 ASR 所需的采样格式。避免把回放参考通道当麦克风。WAV 头必须与实际数据格式一致。
3. **语音端点与识别**：先核实原有候选 Silero VAD / sherpa-onnx VAD，以及 sherpa-onnx 中英文 ASR 模型在本机的适用性，再部署并验证模型、CPU 资源、延迟、语言识别和准确率。当前仅检查了常见命令和进程，未发现运行中的识别服务，不能据此断言电脑不存在其他可用模型。
4. **LLM 回复**：Voice Bridge 不生成对话内容；需要选择并连接本地或用户授权的 LLM 后端，提供对话上下文、超时及错误处理。固定文本或复述只能作为排查中间环节的测试。
5. **Astero 编排与 Bridge 适配**：将采集、ASR、回复及 Bridge 请求接起来，轮询任务至完成或失败，并处理超时、空转录、断线和重复请求。现有 Git 快照中的 Portal 是 dry-run 状态机，`NullSpeaker` 不发声；当前工作区原文件为空，不能把快照视为可运行实现。
6. **唤醒与交互**：本机 `Astero` 自定义唤醒模型、持续监听、前置缓冲与误唤醒校准尚未实现。最初手动触发只是隔离测试，不是最终交互。
7. **回声和打断**：先使用半双工，在播放回复时停止或忽略输入，避免电脑扬声器自触发。电脑播放与 Dot 输入分别位于不同设备，Dot 自身的参考通道不是电脑扬声器的播放参考。AEC、音乐混音、打断和连续追问以后单独验证；Bridge 当前没有公开单任务取消接口。

## 建议的验收顺序

- [ ] 以手动触发录制短句；确认采样格式、实际听感和异常退出后服务恢复。测试录音仅临时保存，完成后删除。
- [ ] 将已知中文和英文短句送入所选 ASR；记录转录及识别耗时，只在测试需要时临时保存内容。
- [ ] 固定文本调用 Voice Bridge：已观察到入队和 `completed`；仍需用户确认电脑扬声器实际发声。
- [ ] 可先串联 Dot → USB → ASR → 固定回复或复述 → Bridge，隔离输入和输出问题。
- [ ] 完成目标闭环：Dot → USB → `Astero` 唤醒 → VAD / ASR → LLM → Bridge → 电脑扬声器。确认识别内容与回复，测量关键时间点及失败路径；播放期间暂停或忽略输入。
- [ ] 测误唤醒、重连、超时、隐私静音和长时间稳定性。

默认不保存原始音频或转录；不把密钥、录音、模型权重或设备序列号写入仓库。
